# Atlas Model

Use Atlas as a modeling tool within the user's planning work. Keep plans, decisions, glossary ownership and lifecycle in the associated planning repository. Link diagram identities to selected passages; embedded context is supporting evidence, not a second authoritative plan.

Prefer the configured Atlas MCP tools, served by `atlas mcp --root <workspace>`. If unavailable, use `atlas model <operation> --root <work folder> --input <request.json|->`; `atlas model tools` lists the operations (MCP names without the `atlas_` prefix) and their JSON contracts. Inside an Atlas checkout, the diagram package's `createWorkspace(root).execute` API also works. If the command is missing, the Atlas README's "Install the atlas command" section explains how to install it. Do not install the command or reconfigure the user's MCP client unless requested.

The work folder is the Atlas workspace root: `createWorkspace(<absolute work folder>)` or `--root <work folder>`, so models live in `<work>/.atlas/models` with revisions in `<work>/.atlas/history` and travel with the work item when it is archived. If the configured MCP root is anything else, use the CLI/API with the work folder. Never create models in the planning root or anywhere outside a work folder; Atlas does not read them. [atlas-organize](../atlas-organize/SKILL.md) moves such models into their work folder and revises their record paths. Do not hand-edit or copy-modify model JSON; change models only through Atlas operations so revisions stay valid.

Load/reopen an existing document before recreating it. `atlas_load` preserves Atlas JSON revisions; `atlas_import` recovers an exported HTML's model without executing the page. Import preserves capture claims and marks them imported; it does not verify an unavailable source. `atlas_inspect` returns handles, revisions and focused elements. Inspect by identity, use small pages, and read a returned file reference only when needed.

Choose `ontouml` for authored conceptual interpretation. Its model is standard OntoUML exchange JSON; use the library's `Project` builders or preserve existing exchange elements. `database` and `code` describe declared source structure with distinct validation. A source-derived snapshot is an explicitly dated baseline within its adapter's supported scope. Do not invent extracted facts, conceptual stereotypes, composition or counts. `?` marks a count that the source cannot establish. Check actual tool availability and adapter coverage before promising source extraction.

Use `atlas_create` for a new document and retain its handle and revision. A diagram exists to explain a plan: always set `workId` to the work folder's registered ID, and link at least one plan section. Stable element IDs link to code evidence and context records; names may change while identities remain. A record is `{ id, kind: "plan" | "glossary" | "decision" | "scenario", title, text, path, section }`, where `path` is relative to the work folder (`plan.md`, `CONTEXT.md`, `docs/adr/0001-x.md`) and `section` is the exact heading text the diagram explains; `context.links` join `elementId` to `recordId`. The Atlas app shows the diagram under that heading. Include only useful passages/excerpts selected for the exported document.

Provenance is derived from the document, so choose its state truthfully. A `snapshot` with profile `code` or `database` shows as **Generated from code** or **Generated from database** (source, capture date, coverage); a `proposal` as **Agent proposal** (changes to its captured baseline); an `authored` document as **Agent-authored** (conceptual for `ontouml`, otherwise structural); an imported document adds "Imported". Never author a model as a snapshot or describe an authored or proposed model as generated from source.

Apply related edits in one `atlas_revise` batch against `expectedRevision`; upsert/delete semantic elements and their references together. OntoUML batches use `elements`; structural batches use their named graph collections. Snapshots remain frozen. On conflict, inspect the current revision and reconcile the intended change rather than retrying with a guessed revision. Model/profile errors require correction; ontology findings remain visible questions rather than a proof of domain accuracy.

Use `atlas_validate` to inspect findings, `atlas_prepare` for a local scene reference consumed by the Atlas app, and `atlas_export` for a self-contained HTML. The Atlas app is a read-only native viewer, not the source of model edits. Explain architectural alternatives and uncertainty in the planning discussion; keep tool mechanics out of the user's decision flow. Saving a document or exporting HTML does not authorize publication, schema changes, implementation, or deployment.

Start iteration with `atlas_proposal` from an explicit baseline. Inspect `atlas_compare` after revising and link consequential changes to selected rationale/evidence. Use `atlas_merge` only with an explicit common ancestor; inspect retained conflicts and resolve named base/left/right choices with `atlas_resolve_merge` against the current revision. `atlas_adopt_snapshot` explicitly selects a newer captured baseline and retains the old one without replacing the proposed model. `atlas_map` expresses an authored link between conceptual and captured elements with a reason; it does not prove implementation equivalence. Baseline, Proposed and Changes share positions in both native and offline viewers.

When a model is difficult to understand, add focused walkthroughs and finite instance/counterexample scenarios through the document's `learning` field, referencing existing context and model/view identities. `atlas_scenarios` assesses declared memberships, numeric counts and complete/disjoint sets; unassessed coverage and mismatched expectations remain visible. Use `reporting.scope` for an explicit submission or review scope. The native/offline Report contains source dates, guided SVG views, examples, glossary, evidence and open questions and can print to PDF. Exported HTML remains editable through Atlas import; do not create a separate authoritative plan inside a report.

For PR/MR architecture review, use `atlas model review --input request.json` or `buildReview` with explicit base/head document files or immutable Git commit/path pairs. Map each source repository by its retained evidence identity and explicit implementation base/head commits. Read the semantic summary, rule/scenario coverage and changed/missing/stale/unassessed evidence. Review artifacts supplement architectural judgment; they neither prove conceptual implementation equivalence nor update a model automatically. Input/command errors exit 2; blocking findings exit 1 while retaining review HTML and original documents. Fetch needed Git objects explicitly before review. Publication, deployment and merge remain separate authorizations.
