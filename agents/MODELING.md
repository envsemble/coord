# Agent workflow

The user specifies one or more source projects and a modeling question in job.json. Inspect those projects and produce an evidence-backed OntoUML model. You are the modeling agent; this package validates and visualizes your output. It does not call a hosted AI or infer an ontology automatically.

1. Read each repository's instructions and identify its revision. Start from the user's domain question, not a one-to-one translation of code classes. Separate software resources, real-world individuals, temporal roles, phases, and events. Record domain terminology.
2. Use standard OntoUML exchange JSON for model.ontouml.json. The installed `ontouml-js` builders can create it programmatically. Its `Project` has a flat `elements` array, a root package ID, and ID references. Inspect the shipped schemas/ontouml-schema.json or the `ontouml-js` declarations. Do not invent a diagram language. Use stable IDs; same names in different projects must remain distinct. Place domains in separate packages and author shared identities and cross-package relations deliberately.
3. State identity, rigidity, dependence, and multiplicities explicitly. A role inherits exactly one identity principle and has a mandatory relationship. Phases form a complete, disjoint partition. A relator requires at least two participants, not necessarily two relation types. Consult https://ontouml.readthedocs.io/en/latest/ when uncertain; the local validator only implements a subset.
4. Write evidence.json separately. Keys under `elements` are model IDs. Each record can contain `evidence`, `primarySource`, `status` (observed/inferred/unresolved), `rationale`, and `questions` with `question`, `why`, and `resolve`. Source records have id, file, title, claim, and optional repo, commit, line, url. Pin GitHub links to full commits. A source observation is evidence for an interpretation, not proof of its stereotype or identity. Record alternative explanations and how to resolve them. See schemas/evidence-schema.json.
5. Optionally cache short, unmodified source excerpts in snippets.json keyed by source ID: `{repo, commit, file, startLine, language, code}`. At most 12 lines per excerpt. The provenance must match its source record. Supported languages include C++, Squirrel, JavaScript, TypeScript, Python, Java, C#, Go, Rust, JSON, Markdown and Text. Missing excerpts are allowed; missing declared source IDs are not. No source files are fetched by the viewer.
6. Optionally write views.json as an array of `{key, label, title, nodeIds, focusIds?, columns?, edgeIds?}`. IDs identify nodes and edges. Columns are placement preferences, never ontology. An empty array creates a default view. Every visible association keeps both multiplicities. The renderer currently supports classes and binary class relations; it rejects unsupported relation shapes instead of silently dropping them.
7. Run `node <library>/bin/ontouml.cjs validate model.ontouml.json --evidence evidence.json --json`. Correct structural errors and assess ontology findings. Keep unresolved findings honest. Then run `node <library>/bin/ontouml.cjs build job.json --out site`. Open site/index.html and inspect routes, labels, source links, and the learning sidebar. This is a read-only visualization; edits belong in the model and evidence files.
8. Deliver the standard model JSON, evidence, validation report and self-contained HTML. Explain which projects/revisions were inspected and what remains unresolved. Do not claim full OntoUML semantic validity, successful model checking, or domain accuracy based only on passing the implemented checks.
