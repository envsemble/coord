# Agent interface

Agents reach Coord through a plugin for their harness: an MCP server for planning state, three skills with the delivery skills beside them, and hooks that run without the agent having to remember anything. One plugin serves Claude Code and Codex, and harnesses that run them, such as T3 Code, load it too. Everything runs on the agent's computer through the [`coord` command](command.md); no hosted service or API key is involved.

## The plugin

The plugin lives in [`plugin/`](../plugin) with a manifest for each harness (`.claude-plugin/plugin.json`, `.codex-plugin/plugin.json`), the MCP server's configuration (`.mcp.json`), the skills (`skills/`) and the hooks: Claude Code reads `hooks/hooks.json`, and Codex reads `hooks/codex.json`, which its manifest names, because the two harnesses offer different events. The repository is its marketplace: `.claude-plugin/marketplace.json` for Claude Code and `.agents/plugins/marketplace.json` for Codex, both named `coord`, so the plugin is `coord@coord`.

The app installs it: its onboarding, and **Settings › Agents** later, connect Claude Code and Codex with the plugin the app carries, a copy in `agent/` of the Coord home that each app update refreshes (and reinstalls into Codex). From a checkout, [`coord setup`](command.md#setup) installs it into each harness on the PATH. By hand, from the checkout:

```sh
claude plugin marketplace add <checkout>
claude plugin install coord@coord
codex plugin marketplace add <checkout>
codex plugin add coord@coord
```

The plugin calls `coord` from the PATH, so [install the command](command.md#install) first. The app's copy calls the command in `agent/` by its full path instead, rewritten as it is copied, in the form each harness runs it: Claude Code's hooks and the MCP server run `bin/coord` (on Windows, the Node.js the app ships running the command, in exec form, since Claude Code runs hooks in Git Bash or PowerShell), and Codex's hooks run `bin/coord` (`bin\coord.cmd` with `cmd.exe /C` on Windows), whose path stays the same across updates. Start a new session after installing. Claude Code reads the plugin from its marketplace folder in place; Codex installs a copy, which `codex plugin add coord@coord` (or `coord setup`) refreshes after the folder changes. Codex asks once to trust the plugin's hooks: type `/hooks` in a new session. It records that in its `config.toml` (`[hooks.state."coord@coord:hooks/codex.json:<event>:<group>:<hook>"]` with `trusted_hash`), and asks again when a hook's command changes; the app reads those entries (never Codex's hash) to warn in Settings › Agents, and otherwise tells from activity: the hooks note in `agent/activity/` of the Coord home when a session starts and at each prompt, and the MCP server when a session first uses its tools.

### Delivery skills

Beside Coord's skills the plugin carries the skills that take a change to a merged PR, and the `reviewer` agent (`plugin/agents/reviewer.md`, Claude Code's) that opus-loop starts. They say nothing of Coord, and Coord's skills say nothing of them: an agent following both draws its conclusions from what happened (a PR merged, the work handed over to finish without the user), so each set holds on its own.

| Skill                                                                | What it is for                                                                                                             | Triggers                                                              |
| -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| [full-send](../plugin/skills/full-send/SKILL.md)                     | Take the work to a merged PR without the user: prove it, review it, file it, babysit it and merge it once its gate passes. | When the user says "full send"                                        |
| [full-stop](../plugin/skills/full-stop/SKILL.md)                     | The same, stopping with the PR ready for the user to merge.                                                                | When the user says "full stop"                                        |
| [babysit-pr](../plugin/skills/babysit-pr/SKILL.md)                   | Watch a PR through CI and review, fixing what is real, with one watcher (`scripts/pr-wait`, or the harness's own).         | When the user asks to watch a PR, or a task waits on one              |
| [opus-loop](../plugin/skills/opus-loop/SKILL.md)                     | A review loop with one reviewer agent before a PR is filed or updated.                                                     | When the user says "opus loop", or full send or full stop asks for it |
| [council](../plugin/skills/council/SKILL.md)                         | Three reviewers at once, with their scores in the PR.                                                                      | When the user says "council"                                          |
| [file-pr](../plugin/skills/file-pr/SKILL.md)                         | A concise PR: its title, a description that leads with the problem, and the model that made it.                            | Whenever a PR is opened or its description rewritten                  |
| [leaving-pr-comments](../plugin/skills/leaving-pr-comments/SKILL.md) | Comments on GitHub on the user's behalf.                                                                                   | Whenever the agent comments on GitHub                                 |

Each skill also runs by its command: `/coord:coord`, `/coord:coord-grill` and `/coord:coord-implement` in Claude Code, `$coord`, `$coord-grill` and `$coord-implement` in Codex. The descriptions of `coord-grill` and `coord-implement` are only their trigger phrases, so the agent picks them when the user says their names and not otherwise; all three allow the agent to invoke them (no `disable-model-invocation`, and `allow_implicit_invocation: true` in `agents/openai.yaml`). Coord's skills name no model or provider. The templates a new planning folder starts from are in the coord package, [`packages/coord/templates/planning`](../packages/coord/templates/planning), with the plan and ledger contract in [`PLANS.md`](../packages/coord/templates/planning/PLANS.md).

## MCP tools

`coord mcp` serves the planning-state operations over stdio; the plugin starts it as the `coord` server. The tools are the same operations as the [`coord work` commands](command.md#planning-state), run in-process:

| Tool             | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `where`          | The projects a folder belongs to (`matches`): each planning folder (an absolute path in the home) with its name, and its active work with their steps and `blocked`, and the project's tags with how many work items carry each; and every active project in the home (`projects`), with its folders and whether it matches, and the active work of those that don't match (with summaries when none matches, to choose from).                                                                                                               |
| `project_create` | Creates a project in the home as the app does, from a name and the folders it covers; the agent asks the user first. Returns its name, planning folder and folders.                                                                                                                                                                                                                                                                                                                                                                          |
| `work_status`    | A work item's plan statuses and dates, its state (whose turn it is), ledger steps, `blocked` and a summary of its statistics. The other work tools return the work item's state without statistics; `step` returns only its steps, progress and `blocked`.                                                                                                                                                                                                                                                                                   |
| `work_create`    | Creates and registers a work item: the next free number, `active/NNNN-slug/plan.md` with a draft header and its `summary`, its ledger with the planning steps, and its `planning.json` entry; `continues` records the work it continues (a [handoff](#handoffs)), `tags` its first tags, `partOf` the work item it is a [part](#parts) of (it becomes the last of that group's parts, in the group's planning folder), and `projects` the [projects it is in](#work-in-several-projects).                                                    |
| `state`          | Says whose turn the work is, its plan's `state` with a line of what for (`note`) and when it was set: `planning` or `working` (the agents'), `waiting` (on a PR's checks or reviews, or something else; with what), `your_turn` (the user's; with what they are to do, such as "Merge owner/repo#12") or `blocked` (with why, which becomes the ledger's `blocked`; any other state clears it). Coord shows it as is and never changes it on its own; see [Whose turn it is](#whose-turn-it-is).                                             |
| `work_update`    | Changes a work item's tags (`addTags`, `removeTags`: lowercase letters, digits, dots and hyphens, such as `0.8.0` or `search`, each written once), the work it continues (`continues`, replacing what was recorded; an empty list records none) its parts (`parts`, in order, replacing them; an empty list records none) or the projects it is in (`projects`, replacing them; an empty list leaves it in the project that keeps it). With tags, it returns the work item's tags and the project's, with how many work items carry each.    |
| `work_search`    | Finds the project's work items, archived ones included, with every tag given (`tags`) and every word of `query` in their number, title, summary or tags; `status` keeps the open (active) or closed (archived) ones. Returns each one's number, title, summary, tags, location, statuses and dates, the latest changed first. It changes nothing, so the hooks leave the session where it is.                                                                                                                                                |
| `work_accept`    | Records that the user accepted the design, marking the planning steps done.                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `work_start`     | Starts implementing an accepted plan: in progress, the agreed steps (at least one) after the ledger's planning steps, in place of the proposed ones; without steps, the proposed steps become them.                                                                                                                                                                                                                                                                                                                                          |
| `step`           | Changes the ledger's steps by `action`: `add` appends todo steps (`steps`; added before implementation starts, they are planning steps), `propose` replaces the plan's proposed steps while it is designed (`steps`; an empty list removes them; shown dimmed and outside the progress until `work_start`), `set` gives a step (`step`, its title) a `status`, `rename` gives it a new title (`to`), and `remove` drops it. A call missing its action's fields is refused with what the action needs.                                        |
| `work_close`     | Closes the work and moves it to `archive/`, with its `outcome`: `complete` (the default; refused with the open items unless its ledger has implementation steps, every step done, and nothing is blocked), `abandoned` (with the `reason`, which goes into the plan's Outcome) or `superseded` (`supersededBy` names the replacement, which alone implies it); a reason without either is refused. Closed work keeps how it ended and declares no state. Follow-ups that move on go into a new work item created with `continues` naming it. |
| `work_reopen`    | Brings archived work back to `active/` with new steps.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |

Every tool but `where` and `project_create` takes an optional `planningFolder` (an absolute path) and `cwd` (the folder the agent works in); without them, the server uses the planning folder of the folder the session started in. A work item named with its project (`envui:work-0048`) is in that project's planning folder, whatever the session's ([work in several projects](#work-in-several-projects)). When several projects match the folder, the tools need the project's `planningFolder` (a work item only one of them registers names its project), and the [coord skill](../plugin/skills/coord/SKILL.md) tells the agent to ask the user which project to plan in. A refusal is a tool error naming the reason and any open items, which the agent can act on. The server's instructions tell the agent to ask the user before creating a work item, to edit prose directly, and to write references in full (`owner/repo#N`, `owner/repo@hash` or their URLs) so Coord links them.

Only planning state has tools. Plan bodies, the ledger's final-review list, glossaries and diagrams are files the agent edits like any other; anything that can be a skill is not a tool. The tools never commit: the agent commits planning changes itself.

To configure an MCP client by hand, start `coord mcp` (on Windows, `node <checkout>/packages/coord/bin/coord.js mcp`). Its stdout carries only MCP messages.

### Handoffs

A plan's header can name the work it continues: follow-ups moved off work that closed, a next phase, deferred review findings.

```yaml
continues: [work-0023, "shop:work-0004"]
```

`work-0023` is work in the same project; `shop:work-0004` is work in another project of the home, named by its planning folder's name (the folder under `~/.coord/planning`, compared case-insensitively on Windows and macOS). The folder's name is unique in the home and stays when the project is renamed in the app, so the reference does too. `work_create` (`coord work create --continues`) and `work_update` (`coord work update --continues`) write it and refuse a reference that names no registered work item, the work item itself, or work that continues it (a loop), and write each reference once, as it resolves (bare in the same project, by the folder's real name in another); `coord check` reports a malformed reference or one naming the work item itself as an error, and warns about one that names no work item and about handoffs that form a loop.

The other direction is derived: the host links each listed work item's `continues` across the home's projects and gives every work item the work that continues it (`continuedIn`), both in the project list's work and in a planning folder's snapshot. Each link carries the project's ID (`projectId`; the same project's too, and `null` only when no project of the home has that folder), its folder's and display name, the work's ID, and its title, state and outcome (`null` when the reference names no work item). A plan that starts or stops continuing one updates the snapshot of the folder it names.

### Parts

A work item can be made of parts: other work items of the same project, in order, each an ordinary work item with its own plan, steps and statuses. The group's plan header lists them; a part records nothing, and knows its group from that list. A handoff says where work went next; parts say what one piece of work is made of.

```yaml
parts: ["work-0034", "work-0035"]
```

`work_create` with `partOf` (`coord work create --part-of`) adds new work as the group's last part, and `work_update` (`coord work update --parts`) sets the parts in order. They refuse work that is not registered in the project, the work item itself, a part listed twice, a part already in another group, a part with parts of its own, and parts for a group that is itself a part: groups are one level deep. `coord check` reports an entry that is not a work ID, the work item itself and a duplicate as errors, and warns about an entry that names no work item, a part listed by two groups and a part with parts of its own. The snapshot's work and the project list's work give each work item its `parts` (in order) and its `partOf` (the group listing it, the first should several; null when none does).

### Work in several projects

A work item is in the project that keeps it: the planning folder its folder is in. Work that involves several projects says so in its plan's header, each project by its planning folder's name, as a handoff names one:

```yaml
projects: ["envui", "internal"]
```

The work is then in exactly those projects, which need not include the one that keeps it; a part has projects of its own, and stays in its group's planning folder. `work_create` and `work_update` (`coord work create --project`, `coord work update --project` or `--no-projects`) write the names as the folders spell them, each once, and refuse a name that is no project of the home; `coord check` reports an entry that cannot name a project and a duplicate as errors, and warns about a name no project of the home has.

`where`, and the session start, list with a project's own active work the active work other projects keep that is in it, each with its `planningFolder` and named with the project that keeps it (`envui:work-0048`). The tools and the `coord work` commands take a work item by that name and then work in that project's planning folder, wherever the session is, so a session never changes its own project's work of the same number; a `planningFolder` given as well must be that project's. In the project list, each work item that lists projects has them linked (`projects`: each with the project's ID, `null` when no listed project has that folder, its folder's name and its display name).

## Hooks

The plugin runs `coord hook <event>` on these events. Each reads the event's JSON from stdin, and never fails the session: a failure is noted in the home's `logs/hooks.log`. The ones that only record what the session does are marked to run in the background (`async`): Claude Code does not wait for them, Codex does. Most hooks finish in [`bin/coord.js`](../packages/coord/bin/coord.js) before any of Coord's TypeScript loads, so each costs about as much as starting Node: a tool use while the session already works, or one of a session no work is linked to, is settled by a small stamp file per session in the home (`session-state/`) without opening the database, and a `PostToolUse` that neither edited a file in the home's planning folders nor called a Coord tool that changes a work item does nothing.

| ----------------------------------------------- | -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

With several projects, it asks the agent to have the user choose the one to plan in. A folder no project covers gets the home's active projects by name and planning folder, with their active work counts, and is told to ask the user which project the work belongs to, or to work across them with `where`; an empty home says so, and how to make a project. It also removes stamp files and log cursors not used for a week. |
| `UserPromptSubmit`                              | Both                                               | A turn starts: the session is working, from now (in the background). The links live in the [home database](command.md#the-coord-home) (a session and the work items it touched), with when each was made; hooks running at once change them in transactions of their own. A report reads the session's logs only from where the previous measurement stopped, keeping a cursor per log in the home's `cache/session-logs/`. A session that edits the plan of accepted work is amending the design, so its next report counts as planning; otherwise the stage follows the plan's design status. [Progress and statistics](progress-and-statistics.md) explains what a report holds and how Coord counts it.

The hooks also record each linked session's turns, for the sessions a plan lists: in a turn from your prompt until it ends or the session does. They say nothing of whose turn the work is, which only its agents declare. A session is on one work item at a time, the one it last edited or changed through a Coord tool: its reports count there. When it moves to another, the one it leaves gets a report up to then, measured at the session's next turn end, prompt or end, so the edit that moved it is not held up; one that cannot be measured then is tried again for a day. The folder the session runs in is kept, so the app can resume it there (`claude --resume <id>`, `codex resume <id>`). Hooks that ran in the background and arrive late change nothing. Codex reviews a plugin's hooks before it runs them: after updating the plugin (`codex plugin add coord@coord` or `coord setup`), trust its changed hooks again.

### Whose turn it is

A plan's header says whose turn its work is, as its agents declare it with `state` (`coord work state`): `planning` or `working` while they are on it, `waiting` while it waits on a PR's checks or reviews or something else, `your_turn` while it waits on you (with what you are to do), `blocked` with why. The tools set the obvious one as they change the work (`work_create`: planning; `work_start` and `work_reopen`: working; `work_accept` and `work_close`: none), and the skills have agents set it at every start and handoff. Coord shows it as it is, with when it was set, and never changes it on its own: the hub groups work by it, and the plan page says it under the title.

Since nothing corrects a state but an agent, the session start names what no longer adds up in the project's active work, for the agent to bring up and fix: work under way that declares no state, every step done but still open, your turn for more than three days, `working` or `planning` declared more than a day ago with no change to the plan since, and a draft whose implementation started. It reads only the plans and ledgers, so the session starts quickly; a PR its state names shows its live state on the plan page.

## The home and how agents reach it

All planning folders live in the **Coord home**, `~/.coord/planning/<name>` (or under `COORD_HOME`), each its own Git repository and each a **project**: named by the `name` in its `planning.json` (else the folder's name), and covering the folders on this computer where its work happens. [The command reference](command.md#the-coord-home) lists what else the home holds.

An agent usually works in a product checkout or a worktree elsewhere, so its harness has to let it write into the home. `coord setup` grants the home once, to every session: as an additional directory in Claude Code (`permissions.additionalDirectories`) and as a writable root in Codex (`[sandbox_workspace_write] writable_roots`). The agent then edits planning files at their absolute paths from any checkout. The MCP server runs outside the harness's sandbox, so the tools' own writes do not depend on that grant.

`coord home` lists the projects. New projects are made in the app, by `coord project create`, or by an agent with the `project_create` tool once the user agrees; a project made outside the app shows up in it at once.

## How a checkout finds its planning folder

A session whose folder is one of a project's **folders** (`folders` in its `planning.json`, absolute paths) or inside one belongs to that project. When folders nest, the deepest wins; two projects covering the same folder both match. Paths compare case-insensitively on Windows and macOS. A session inside a planning folder belongs to that project. Outside every folder, a session belongs to no project: the agent asks the user. Git remotes play no part, and a project registers no repositories.

Only active projects in the home match: archived projects (such as a planning folder split into several projects) never do.

A worktree belongs to a project only when it is inside one of its folders. The active work shown is the work under `active/`. When several projects match, `where` and the session context list them all by name; an operation on a work item uses the one that registers it, and otherwise needs the project's planning folder: the agent asks the user which project to plan in. When none matches, it asks for the planning folder explicitly. Matching or not, `where` also lists every active project in the home, so an agent outside any project can ask which one the work belongs to, or go through them all. `coord where` shows the result for the current folder.
