# Agent interface

Agents reach Atlas through a plugin for their harness: an MCP server for planning state, three skills, and hooks that run without the agent having to remember anything. One plugin serves Claude Code and Codex, and harnesses that run them, such as T3 Code, load it too. Everything runs on the agent's computer through the [`atlas` command](command.md); no hosted service or API key is involved.

## The plugin

The plugin lives in [`plugin/`](../plugin) with a manifest for each harness (`.claude-plugin/plugin.json`, `.codex-plugin/plugin.json`), the MCP server's configuration (`.mcp.json`), the hooks (`hooks/hooks.json`) and the skills (`skills/`). The repository is its marketplace: `.claude-plugin/marketplace.json` for Claude Code and `.agents/plugins/marketplace.json` for Codex, both named `atlas`, so the plugin is `atlas@atlas`.

[`atlas setup`](command.md#setup) installs it into each harness on the PATH. By hand, from the checkout:

```sh
claude plugin marketplace add <checkout>
claude plugin install atlas@atlas
codex plugin marketplace add <checkout>
codex plugin add atlas@atlas
```

The plugin calls `atlas` from the PATH, so [install the command](command.md#install) first. Start a new session after installing. Claude Code reads the plugin from the checkout in place; Codex installs a copy, which `codex plugin add atlas@atlas` (or `atlas setup`) refreshes after the checkout changes.

### Skills

| Skill                                                        | What it is for                                                                                                                                                                                                                                                                       | Triggers                                                                                                                                                             |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [atlas](../plugin/skills/atlas/SKILL.md)                     | Everything an agent needs to know about Atlas: finding the planning folder, recording plans, glossaries, decisions and knowledge, the Atlas tools, statistics, setting up and organizing projects, diagrams, and work across projects (reviewing them and bringing them up to date). | On its own: when the user mentions Atlas, a project, a work item, a plan or a ledger, designs something, or wants something recorded, reviewed or brought up to date |
| [atlas-grill](../plugin/skills/atlas-grill/SKILL.md)         | The questioning workflow: rounds over a design tree, one decision at a time with a recommendation, recording as answers settle, until the plan is ready to accept.                                                                                                                   | When the user says "atlas grill", "grill" or "grill me"                                                                                                              |
| [atlas-implement](../plugin/skills/atlas-implement/SKILL.md) | Implementing an accepted plan end to end: its steps, reviews, PRs and closing.                                                                                                                                                                                                       | When the user says "atlas implement"; never for ordinary coding                                                                                                      |

Each skill also runs by its command: `/atlas:atlas`, `/atlas:atlas-grill` and `/atlas:atlas-implement` in Claude Code, `$atlas`, `$atlas-grill` and `$atlas-implement` in Codex. The descriptions of `atlas-grill` and `atlas-implement` are only their trigger phrases, so the agent picks them when the user says their names and not otherwise; all three allow the agent to invoke them (no `disable-model-invocation`, and `allow_implicit_invocation: true` in `agents/openai.yaml`). The skills name no model or provider. The planning templates a new planning folder starts from are in [`plugin/skills/atlas/assets/planning`](../plugin/skills/atlas/assets/planning), with the plan and ledger contract in [`PLANS.md`](../plugin/skills/atlas/assets/planning/PLANS.md).

## MCP tools

`atlas mcp` serves the planning-state operations over stdio; the plugin starts it as the `atlas` server. The tools are the same operations as the [`atlas work` commands](command.md#planning-state), run in-process:

| Tool                                                 | What it does                                                                                                                                                                                                                                                                                                                                                      |
| ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `where`                                              | The projects a checkout belongs to (`matches`): each planning folder (an absolute path in the home) with its name, and the active work for its repositories with their steps and `blocked`; and every active project in the home (`projects`), with its repositories, workspace folders, its active work as titles, summaries and states, and whether it matches. |
| `project_create`                                     | Creates a project in the home as the app does, from a name and workspace folders, registering the Git checkouts in them (or the repositories given); the agent asks the user first. Returns its name, planning folder, workspace folders and repositories.                                                                                                        |
| `work_status`                                        | A work item's plan statuses and dates, ledger steps, `blocked` and a summary of its statistics.                                                                                                                                                                                                                                                                   |
| `work_create`                                        | Creates and registers a work item: the next free number, `active/NNNN-slug/plan.md` with a draft header and its `summary`, its ledger with the planning steps, and its `planning.json` entry; `continues` records the work it continues (a [handoff](#handoffs)).                                                                                                 |
| `work_accept`                                        | Records that the user accepted the design, marking the planning steps done.                                                                                                                                                                                                                                                                                       |
| `work_start`                                         | Starts implementing an accepted plan: in progress, the agreed steps (at least one) after the ledger's planning steps.                                                                                                                                                                                                                                             |
| `step_add`, `step_set`, `step_rename`, `step_remove` | Change the ledger's steps (added before implementation starts, they are planning steps).                                                                                                                                                                                                                                                                          |
| `work_block`                                         | Sets the ledger's `blocked`, or clears it without a reason.                                                                                                                                                                                                                                                                                                       |
| `work_continue`                                      | Records which work a work item continues, its plan's `continues`, replacing what was recorded; an empty list records none.                                                                                                                                                                                                                                        |
| `work_close`                                         | Closes finished work: refused with the open items unless its ledger has implementation steps, every step done, and nothing is blocked; then complete, and moved to `archive/`. Follow-ups that move on go into a new work item created with `continues` naming it; closing records nothing more.                                                                  |
| `work_archive`                                       | Moves work to `archive/` without closing it: `superseded` (with the work that replaces it, which alone implies it) or `abandoned` (with the reason), which becomes the plan's design status, the reason going into the plan's Outcome. A reason without a disposition is refused.                                                                                 |
| `work_reopen`                                        | Brings archived work back to `active/` with new steps.                                                                                                                                                                                                                                                                                                            |

Every tool but `where` and `project_create` takes an optional `planningFolder` (an absolute path) and `cwd` (the checkout the agent works in); without them, the server uses the planning folder of the folder the session started in. When several projects match the checkout, the tools need the project's `planningFolder` (a work item only one of them registers names its project), and the [atlas skill](../plugin/skills/atlas/SKILL.md) tells the agent to ask the user which project to plan in. A refusal is a tool error naming the reason and any open items, which the agent can act on. The server's instructions tell the agent to ask the user before creating a work item and to edit prose directly.

Only planning state has tools. Plan bodies, the ledger's final-review list, glossaries, ADRs, knowledge and diagrams are files the agent edits like any other; anything that can be a skill is not a tool. The tools never commit: the agent commits planning changes itself.

To configure an MCP client by hand, start `atlas mcp` (on Windows, `node <checkout>/packages/atlas/bin/atlas.js mcp`). Its stdout carries only MCP messages.

### Handoffs

A plan's header can name the work it continues: follow-ups moved off work that closed, a next phase, deferred review findings.

```yaml
continues: [work-0023, "shop:work-0004"]
```

`work-0023` is work in the same project; `shop:work-0004` is work in another project of the home, named by its planning folder's name (the folder under `~/.atlas/planning`, compared case-insensitively on Windows and macOS). The folder's name is unique in the home and stays when the project is renamed in the app, so the reference does too. `work_create` (`atlas work create --continues`) and `work_continue` (`atlas work continue`) write it and refuse a reference that names no registered work item or the work item itself; `atlas check` reports a malformed reference or one naming the work item itself as an error, and warns about one that names no work item and about handoffs that form a loop.

The other direction is derived: the host links each listed work item's `continues` across the home's projects and gives every work item the work that continues it (`continuedIn`), both in the project list's work and in a planning folder's snapshot. Each link carries the project's folder ID (`null` within the same project), its folder's and display name, the work's ID, and its title, state and outcome (`null` when the reference names no work item). A plan that starts or stops continuing one updates the snapshot of the folder it names.

## Hooks

The plugin runs `atlas hook <event>` on these events. Each reads the event's JSON from stdin, and never fails the session: a failure is noted in the home's `logs/hooks.log`. The ones that only record what the session does are marked to run in the background (`async`): Claude Code does not wait for them, Codex does. They load only what they need, and a tool use while the session already works, or one of a session no work is linked to, is settled by a small stamp file in the home (`session-state/`) without opening the database, so each costs about as much as starting Node.

| Event               | What Atlas does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --- |
| `SessionStart`      | Tells the agent each project its checkout [belongs to](#how-a-checkout-finds-its-planning-folder) (its name and planning folder, an absolute path), its active work with each item's statuses, progress, steps being done and anything blocked, and how to plan: ask before opening a work item, change state through the tools, edit prose and diagrams as files, and record a [handoff](#handoffs) when opening work that continues other work. With several projects, it asks the agent to have the user choose the one to plan in. A folder no project registers gets the home's active projects by name and planning folder, with their active work counts, and is told to ask the user which project the work belongs to, or to work across them with `where`; an empty home says so, and how to make a project.                                                                                              |
| `UserPromptSubmit`  | A turn starts: the session is working, from now (in the background).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `PostToolUse`       | After a file edit (`Edit`, `Write`, `MultiEdit`, `NotebookEdit`, or a patch) or an Atlas tool call: checks every edited file in the home's planning folders (those with a `planning.json`; other files in the home are left alone) with the same rules as `atlas check`, and hands any problems back so the agent fixes them (what the check only warns about, such as an active plan without a summary, is passed on without stopping the agent); and links the session to the work item the file belongs to or the tool changed (reading one, `work_status`, does not). After every tool use, also a failed one (`atlas hook ToolUse`, in the background), notes that the session is working, at most once a minute while it already is, and records the commits it makes (`git commit` prints `[branch hash] subject`) and the PRs it opens (`gh pr create` prints the URL) for the work item the session is on. |
| `Notification`      | Claude Code's permission and idle prompts: the session waits for you, within its turn (in the background).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `PermissionRequest` | The same when the session asks for permission; Codex, which has no `Notification`, says so this way (in the background).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `Stop`              | The turn is over: the session waits for you from now. The turn's last message (the hook's input has it; else the end of a Claude Code log) is kept while the session waits (at most a day), for the plan page. Then records a statistics report for the work item the session is on, measured from the session's log since its previous report there, or since the session came to it. `StopFailure` (Claude Code: the turn ended on an error) and `Interrupt` (Codex: you interrupted it) do the same.                                                                                                                                                                                                                                                                                                                                                                                                             |
| `SubagentStart`     | A subagent starts: it works for its session, on the work item the session is on (in the background).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `SubagentStop`      | Records the same report when one of the session's subagents stops, so its work is counted while the session goes on; the session's state stays as it is. The subagent is no longer at work.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |     |
| `SessionEnd`        | The session ended: it neither works nor waits.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |

The links live in the [home database](command.md#the-atlas-home) (a session and the work items it touched), with when each was made; hooks running at once change them in transactions of their own. A session that edits the plan of accepted work is amending the design, so its next report counts as planning; otherwise the stage follows the plan's design status. [Progress and statistics](progress-and-statistics.md) explains what a report holds and how Atlas counts it.

The hooks also record each linked session's state for the app's statuses, at once: **working** from the start of a turn until it ends, still working while it is seen within the last 15 minutes (which covers a long tool call); **waiting** for you after the turn ends or while it asks for permission, until you reply, the session ends, or a day has passed. A session's subagents (Claude Code names them in their hooks) are tracked on their own: from their start, each tool use of theirs says they are still at work, and their stop ends it; one not seen for 15 minutes has most likely stopped. While any of them works, the plan is working, whatever the main agent does: it may have ended its turn to wait for them. A session is on one work item at a time, the one it last edited or changed through an Atlas tool: its state, live time and reports count there, and when it moves to another, the one it leaves gets a report up to then. Waiting ends early when another session works on the plan. Each wait is recorded with the work item the session was on, and the folder the session runs in is kept, so the app can resume it there (`claude --resume <id>`, `codex resume <id>`). Hooks that ran in the background and arrive late change nothing. A harness without some of these events falls back on `Stop` and on waiting expiring after a day. What the hooks cannot see: in Claude Code, a permission you grant for a long tool call shows as waiting until that call ends (no hook runs on approval), and a turn you interrupt shows as working for up to 15 minutes, until you write again (no hook runs on an interruption). Codex reviews a plugin's hooks before it runs them: after updating the plugin (`codex plugin add atlas@atlas` or `atlas setup`), trust its changed hooks again.

## The home and how agents reach it

All planning folders live in the **Atlas home**, `~/.atlas/planning/<name>` (or under `ATLAS_HOME`), each its own Git repository and each a **project**: named by the `name` in its `planning.json` (else the folder's name), covering one repository or several and the workspace folders on this computer where its work happens. A repository may belong to several projects, all equal; a workspace folder decides which one a session is in. [The command reference](command.md#the-atlas-home) lists what else the home holds.

An agent usually works in a product checkout or a worktree elsewhere, so its harness has to let it write into the home. `atlas setup` grants the home once, to every session: as an additional directory in Claude Code (`permissions.additionalDirectories`) and as a writable root in Codex (`[sandbox_workspace_write] writable_roots`). The agent then edits planning files at their absolute paths from any checkout. The MCP server runs outside the harness's sandbox, so the tools' own writes do not depend on that grant.

`atlas home` lists the projects, and `atlas home adopt <folder>` moves an existing planning folder into the home. New projects are made in the app, by `atlas project create`, or by an agent with the `project_create` tool once the user agrees; a project made outside the app shows up in it at once.

## How a checkout finds its planning folder

A session whose folder is one of a project's **workspace folders** (`workspaces` in its `planning.json`, absolute paths) or inside one belongs to that project, and to no other: a workspace folder takes precedence over remotes. When workspace folders nest, the deepest wins; two projects covering the same folder both match. Paths compare case-insensitively on Windows and macOS. Outside every workspace folder, a checkout belongs to a planning folder in the home when:

- **its Git remote** is registered as a repository's `remote` in that folder's `planning.json`. Remotes compare by host, owner and name, so `git@github.com:owner/repo.git` and `https://github.com/owner/repo` match;
- or, for a repository registered without a remote, its absolute `path` is the checkout;
- or the session works inside the planning folder itself.

Only active projects in the home match: archived projects (such as a planning folder split into several projects) never do. A project the app lists outside the home, from before it, is not found by agents at all; move it into the home first (**Move into the Atlas home** in its context menu, or `atlas home adopt <folder>`).

A worktree has its checkout's remotes, so it finds the same folder wherever it is. The active work shown is the work under `active/` for the matching repositories. When several projects match, `where` and the session context list them all by name; an operation on a work item uses the one that registers it, and otherwise needs the project's planning folder: the agent asks the user which project to plan in. When none matches, it asks for the planning folder explicitly. Matching or not, `where` also lists every active project in the home, so an agent outside any project can ask which one the work belongs to, or go through them all. `atlas where` shows the result for the current folder.
