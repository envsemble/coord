# The atlas command

One `atlas` command serves agents, their harnesses and scripts: the planning-state operations (also served over MCP), checks, the harness hooks and setup, plan export and import, work and consultation reports, and the Atlas host. It needs only Node 24.

## Install

From a checkout:

```sh
npm ci
npm link --workspace @envsemble/atlas
atlas --version
atlas setup
```

`npm link` puts `atlas` on the PATH (Windows and Linux) as a link to this checkout, so keep the checkout in place; it always runs the checkout's current code. `npm rm --global @envsemble/atlas` removes it. Inside the checkout, `npx atlas …` works without linking. `atlas setup` then makes Atlas part of every agent session on this computer; see [below](#setup).

On Windows the link is a `.cmd`/`.ps1` shim that only shells can run. An MCP client you configure by hand should start `node <checkout>/packages/atlas/bin/atlas.js mcp` instead.

## Commands

```text
atlas where [--cwd <dir>]
atlas project create --name <name> --workspace <folder>... [--json]
atlas work status <work-id> [--planning-dir <dir>]
atlas work create --title <title> [--summary <text>] [--repo <id>...] [--slug <slug>] [--planning-dir <dir>]
atlas work accept <work-id> [--planning-dir <dir>]
atlas work start <work-id> --step <title>... [--planning-dir <dir>]
atlas work step add <work-id> <title>... [--planning-dir <dir>]
atlas work step set <work-id> <title> <todo|doing|done> [--planning-dir <dir>]
atlas work step rename <work-id> <title> <new-title> [--planning-dir <dir>]
atlas work step remove <work-id> <title> [--planning-dir <dir>]
atlas work block <work-id> (<reason> | --clear) [--planning-dir <dir>]
atlas work close <work-id> [--planning-dir <dir>]
atlas work archive <work-id> [--superseded-by <work-id> | --abandoned] [--reason <why>] [--planning-dir <dir>]
atlas work reopen <work-id> --step <title>... [--planning-dir <dir>]
atlas check [<path>...]
atlas home [list]
atlas home adopt <folder> [--name <name>]
atlas mcp
atlas hook <SessionStart|UserPromptSubmit|PostToolUse|ToolUse|Notification|PermissionRequest|Stop|StopFailure|Interrupt|SubagentStart|SubagentStop|SessionEnd>
atlas setup [--dry-run]
atlas planning check <planning-root>
atlas plan export <work-id|work-folder> [--planning-dir <dir>] [--out <file>] [--force]
atlas plan import <file> [--planning-dir <dir>] [--dry-run]
atlas usage log <planning-root> --files <path>... [--task <id>] [--session <id>] [--home <dir>]
atlas work report <planning-root> --work <work-id> [--step <title>] [--model <model>] [--session <id>] [--tokens <n>]
atlas serve [--address <ip>] [--port <n>] [--home <dir>]
atlas --version
atlas help
```

### Planning state

These are the operations the [MCP server](agent-interface.md#mcp-tools) offers as tools, called in-process. Each prints the work item's status as JSON (the `where` command prints the projects it found), never commits, and exits 0 on success, 1 when the operation is refused (with the reason, and any open items, on stderr) and 2 on usage errors. They use the planning folder given by `--planning-dir`, else the one the current checkout [belongs to](agent-interface.md#how-a-checkout-finds-its-planning-folder).

| Command                | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `atlas where`          | The projects in the Atlas home that this checkout belongs to (by a workspace folder of theirs it is in, which decides alone, else by its Git remotes, by an absolute path hint, or by being inside one), each with its name, planning folder, active work, steps and anything blocked (`matches`), and every active project in the home in brief (`projects`: its name, planning folder, repositories, workspace folders, active work as titles, summaries and states, and whether it matches). It works outside a Git checkout too. `--cwd` asks for another folder.                                                                       |
| `atlas work status`    | A work item's plan statuses and dates, ledger steps, `blocked`, and a summary of its statistics.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `atlas project create` | Creates a project in the home, as the app does: a planning folder from the bundled templates, as its own Git repository with a first commit, covering the `--workspace` folders (relative ones are resolved from the current folder) and registering the Git checkouts in them (each folder itself and the folders directly inside it; worktrees and clones count once, by their remote). Prints its name, planning folder, workspace folders and repositories, as JSON with `--json`; a checkout Git does not answer for (it times out, or Git refuses another user's folder) is skipped and named on stderr. A missing folder is refused. |
| `atlas work create`    | Registers new work under the next free number: `active/NNNN-<slug>/plan.md` with a draft plan header (with `--summary`, two or three sentences on what the work is, why and where it stands), its ledger with the planning steps, and its `planning.json` entry. `--repo` names its repositories; by default, the ones this checkout is.                                                                                                                                                                                                                                                                                                    |
| `atlas work accept`    | Records that the design was accepted: `design_status: accepted` and `accepted_at` today, and every planning step done. Only a draft can be accepted.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `atlas work start`     | Starts implementing an accepted plan: `implementation_status: in_progress`, the given steps (at least one, all `todo`) after the ledger's planning steps (in a new ledger for older work without one).                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `atlas work step …`    | Adds steps (planning steps before implementation starts, implementation steps after), sets one to `todo`, `doing` or `done`, renames one, or removes one.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `atlas work block`     | Sets the ledger's `blocked` to the reason, or clears it with `--clear`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `atlas work close`     | Closes finished work: refused, with the open items, unless its ledger has implementation steps, every step done, and nothing is blocked; then the implementation is complete, `completed_at` is today, and the folder moves to `archive/` with its links repaired.                                                                                                                                                                                                                                                                                                                                                                          |
| `atlas work archive`   | Moves a work folder from `active/` to `archive/` without closing it. Work that is not complete needs a disposition: `--superseded-by` the work that replaces it, or `--abandoned` with `--reason`; `--reason` goes only with one of them. It becomes the plan's `design_status` (and `superseded_by`), and the reason goes into the plan's Outcome.                                                                                                                                                                                                                                                                                         |
| `atlas work reopen`    | Moves archived work back to `active/`, in progress, with the new steps as `todo`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `atlas check`          | Checks plans, ledgers and the registry of the files or planning folders given (default: this checkout's), including that archived work is complete, superseded or abandoned rather than left open, and warns about active plans without a `summary` and diagrams no document links. Read-only. Exits 0 when valid, 1 on errors, 2 on usage errors.                                                                                                                                                                                                                                                                                          |
| `atlas home`           | Prints where the Atlas home is and its projects: each one's name and planning folder.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `atlas home adopt`     | Moves an existing planning folder (the top of a Git repository with a `planning.json`) into the home, as `--name` or under its own name. Relative repository paths pointing outside it become absolute. Its `.atlas/statistics.jsonl` files go into the home database and are deleted; commit that. A project whose folder is gone but was last at the new path is taken for this folder renamed or moved by hand: the folder takes over its statistics, and the command says so. If the folder has a project of its own, that is another project, and the command refuses; choose another `--name`.                                        |
| `atlas planning check` | The older check of one planning folder: its registry and plan and ledger headers. Read-only; 0 valid, 1 errors, 2 usage errors.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

### Agents and harnesses

| Command             | What it does                                                                                                                                                                                                                                                            | Exit codes                               |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| `atlas mcp`         | Serves the planning-state operations to an agent harness over stdio. See the [agent interface](agent-interface.md).                                                                                                                                                     | Runs until the client closes it; 2 usage |
| `atlas hook`        | Runs one harness hook on the JSON the harness writes to its stdin; the [plugin](agent-interface.md#hooks) calls it. It never breaks a session: on any failure it prints nothing and notes the failure in the home's `logs/hooks.log`.                                   | Always 0                                 |
| `atlas setup`       | Creates the Atlas home, grants it to Claude Code and Codex, and installs the Atlas plugin into each harness on the PATH. `--dry-run` prints what it would do.                                                                                                           | 0, 1 when a step failed                  |
| `atlas work report` | Records a statistics report for a work item by hand, for agents whose harness runs without the plugin's hooks. Inside Claude Code or Codex it measures the session from its log. See [progress and statistics](progress-and-statistics.md#reporting-without-the-hooks). | 0, or 2 for usage errors                 |
| `atlas usage log`   | Records which planning documents an agent consulted, for the app's Document use statistics. Never fails the task: gaps are reported on stderr.                                                                                                                          | 0, or 2 for usage errors                 |

### Sharing and serving

| Command             | What it does                                                                                                                                                                                                       | Exit codes                                                                                                                                                                                                                                                                                                 |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `atlas plan export` | Writes a whole work item to one self-contained `.atlas-plan.html` file (by default `<slug>-<work-id>.atlas-plan.html` in the current folder; an existing file needs `--force`). See [plan export](plan-export.md). | 0, 1 when the export fails (an unknown work item, an existing file without `--force`, a refused folder), 2 usage errors                                                                                                                                                                                    |
| `atlas plan import` | Previews an export, then adds it as new work under the next free number and registers it, without committing; `--dry-run` only previews.                                                                           | 0, 1 invalid export or refused folder, 2 usage errors                                                                                                                                                                                                                                                      |
| `atlas serve`       | Runs the Atlas host without the desktop app, so paired devices can work on this computer's projects. It prints a one-time pairing link with a QR code. See [remote access](remote-access.md).                      | Runs until stopped; 1 when it cannot start (no Tailscale address without `--address`, the app already manages remote access, it cannot listen, or Atlas's settings still wait to be moved: in the old data folder, with the default home, or in the home's files from before its database), 2 usage errors |

`plan export` and `plan import` use the planning folder given by `--planning-dir`, else the current folder.

## Setup

`atlas setup` makes Atlas part of every agent session on this computer, and changes nothing when run again:

1. It creates the [Atlas home](#the-atlas-home), moving Atlas's files from the old data folder into it, then moves the home's own files into its database and imports the work statistics files of the planning folders in the home, deleting them there (the commits are yours to make). Planning folders outside the home are left alone: their statistics files are imported when they move in (`atlas home adopt`, or **Move into the Atlas home** in the app). While an Atlas app or `atlas serve` uses that folder and settings still wait there, setup refuses and asks you to quit it first (it cannot tell an older Atlas from the current one); with only logs and statistics left, it moves them on a later run.
2. It grants the home to **Claude Code** (`permissions.additionalDirectories` in its `settings.json`) and **Codex** (`[sandbox_workspace_write] writable_roots` in its `config.toml`, or `sandbox_workspace_write.writable_roots` where that table is written as dotted keys), so agents in any checkout or worktree can edit planning files there. It edits only that list, or adds the key, and leaves the rest of each file's text as it was.
3. For each harness on the PATH, it adds this checkout as the `atlas` plugin marketplace and installs the `atlas@atlas` plugin through the harness's own commands. Claude Code reads the plugin from the checkout in place. Codex installs a copy, so run `atlas setup` again after updating the checkout to refresh it; a Codex marketplace named `atlas` added from another checkout is replaced by this one.

A harness that is neither on the PATH nor configured is skipped. `HOME` (`USERPROFILE` on Windows), `CLAUDE_CONFIG_DIR`, `CODEX_HOME` and `PATH` choose what it touches. Start a new agent session afterwards to load the plugin.

## The Atlas home

The **Atlas home** is `~/.atlas`, or `ATLAS_HOME` when set (`--home` for `usage log` and `serve`). It holds:

- `planning/<name>/`: the planning folders, each its own Git repository and each a project;
- `atlas.db`: the home database (SQLite), with everything else Atlas keeps: the projects (their names, order and whether they are archived, and the projects of paired computers), the host's identity and paired devices, the app's connections, windows and tabs, which work items each agent session has touched and when it last did, whether its agent is in a turn or waits for you (the work's Working and Needs you), work statistics reports and document-use statistics;
- `logs/`: the app's, the host's and the hooks' logs;
- `legacy/`: files from the old data folder that the home already had its own of, and the home's files from before its database.

Every process opens the database as it needs it, so the app, the host, the CLI and the hooks share it. It holds secrets (the host's, paired devices' token hashes, the app's connection tokens), so on macOS and Linux the home is created readable by you only and the database files are kept at 0600. Its schema has a version; an older Atlas refuses a newer database rather than change it, unless the newer one only added tables and columns, which it leaves alone. Homes from before the database had `sessions/`, `usage/`, `host/`, `connections.json`, `planning-roots.json` and `desktop-state.json`; the app as it starts and `atlas setup` move them into the database and set the files aside in `legacy/` (while an older `atlas serve` still uses them, both refuse and ask you to stop it, and `atlas serve` itself refuses to start until they have moved).

Atlas used to keep these files in a per-user data folder (`%APPDATA%\Atlas` on Windows, `~/Library/Application Support/Atlas` on macOS, `${XDG_CONFIG_HOME:-~/.config}/Atlas` on Linux). With the default home, they move into it when the installed desktop app starts (it shares the older app's single-instance lock, so the older app is not running then) or when `atlas setup` runs (refused while an older app or `atlas serve` runs); never from a development run of the app (`npm run dev`), other commands, the host or the hooks. While its settings (`host/`, `connections.json`, `desktop-state.json`, `planning-roots.json`) wait to be moved, neither the app nor `atlas serve` starts on the default home, so neither fills it with fresh settings that would push the user's own aside (a refused start may still create the home's empty `planning/` and its `logs/`): a development run and `atlas serve` say to run `atlas setup` first (or to set a home of their own), and the installed app says to stop an older `atlas serve` that still uses the folder, or to close whatever holds a file it could not move. Usage statistics move per planning folder, merged with the home's own for a folder the home already has; nothing else in the home is overwritten, the old copy goes to `legacy/` instead (numbered, `legacy/host.2`, when a copy of the same name is there already). The app's log records what moved. Electron's own caches stay in that folder.

Work statistics reports are in the home database, under the work item's project. Planning folders used to keep them as `<work>/.atlas/statistics.jsonl`; `atlas setup` (for the planning folders in the home) and `atlas home adopt` (as it moves a folder in) import those files and delete them, and Atlas never commits, so commit the removal in the planning folder.
