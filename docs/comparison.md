# Proposals and comparison

Create a proposal with `createProposal(baseline)` or `atlas_proposal`. Source snapshots stay frozen. An authored reference model is frozen explicitly with an `atlas-authored-baseline` label; this is not an extraction claim. A proposal opens in its change view: the proposal with the baseline's removed entities, members and routes retained, laid out once over both states in the document's authored views (or the baseline's). Removed entities stay in a view the baseline showed them in or next to their former neighbors; anything outside every view appears in an extra "All elements" view, and documents without views get one combined view. To see the baseline itself, open the captured model it was taken from. Added, changed and removed elements have green, amber and red borders with a New, Changed or Removed tag, kept through hover and selection; with fields shown, each member is marked too. Changed relations take the same colours and carry a +, ~ or − on the line, so no change rests on colour alone; a removed relation is dotted. A relation that keeps its ends and changes only its name or counts is drawn once, marked changed. Unchanged elements fade until that toggle is turned off. The **Changes** list, open beside the diagram when the window has room, has one row per changed element: new, changed and removed types with their members summarized (`+ vault, + pay()`), then relations as `Source → Target`, and unresolved merge choices first. OntoUML attributes and relation ends are listed with their class or relation. Values read by name, before → after (`name: Student → Pupil`). Changes to the model itself, such as its constraints or an OntoUML package's name, are listed under **Model**. Choosing a row selects and reveals the element; its details step to the previous or next change and back to the list. A change no view draws, such as a relation between classes shown in different views, is listed but cannot be opened or stepped to; the **Changes** button counts the changes that can be opened and any unresolved conflicts. The view opens on what changed when the whole diagram is too large to read at once.

Comparison matches stable IDs, including fields, methods, relation properties and generalization sets. Names do not establish identity. Coordinates, source positions and diagram records are presentation; counts, types, stereotype and generalization-set constraints are semantic. `compareModels` supplies raw differences; `compareDocuments` also attaches evidence and selected context. `atlas_compare` returns a paginated change list, defaulting to the proposal's retained baseline. Comparison views show separate inheritance arrows to keep changed routes unambiguous; ordinary views still support named joined inheritance.

`mergeDocuments(ancestor, left, right)` requires explicit common ancestry. Independent property changes, identified collections and evidence reference sets combine. Conflicting values and delete-versus-modify choices remain in a valid draft with base/left/right values. If combined changes break references, a complete-payload choice preserves valid inputs. `resolveMerge` / `atlas_resolve_merge` applies explicit choices using the expected revision; remaining conflicts stay visible. Resolving an invalid choice fails atomically. No fuzzy matching or silent conflict resolution occurs.

`adoptSnapshot` / `atlas_adopt_snapshot` explicitly selects a newer captured baseline of the same profile. It retains older captures, context and adoption history and leaves the proposed model unchanged. Competing baseline adoptions are merge conflicts. `linkMapping` / `atlas_map` links a current element to an element in a retained capture, including a different profile, with an authored reason. This expresses a design interpretation, not automatic OntoUML classification or proof that code implements a plan.

Offline HTML retains proposals, all included captures, mappings and conflicts. Import recovers their data without executing the viewer. The viewer only inspects these states; agents edit through the library or workspace tools. Expected-revision checks protect persisted edits and conflict choices.
